You need no wallet, no test tokens and no install. Your browser makes a throwaway identity and our sponsor account pays its first fees.

## The two-minute path

Steps 1 and 2 take about two minutes. Step 3 adds about ninety seconds of waiting for blocks.

1. Open [Attack it](/proof). As the page loads, your browser runs four checks against the chain and shows each answer.
   - A change with no ML-DSA-87 signature, sent from the chair's own address and from a stranger's. Both are refused with `BadSignature`.
   - The demo board's newest real change, sent again byte for byte. Refused, with the registry's own reason.
   - One real signature tried on five messages. The chain and your browser agree: valid once, and never again.
   - The newest pack as we store it, hashed in your browser. It is the same hash the chain holds.
2. Open [the demo board](/demo). Type any passphrase of ten characters or more and press **Make my identity and join**. Six chapters run on screen: your identity is made, funded, its two keys go on chain, you sign the chair's challenge, you are admitted, and a pack sealed to you opens on your device.
3. Press **Leave the board**. Your browser signs your own removal, the board gets a new key, and the next pack is posted. Your browser then tries every key it holds on that pack and shows that none opens it.
4. Open [your board room](/board) to run a board of your own: create it, add a director by address, post any file, remove the director, and read the ledger.

Each change to a board takes about half a minute. The page says what it is doing while you wait.

## The Encrypted Apps requirements

| Requirement | Where it is |
|---|---|
| ML-KEM-1024 encryption | Each board key is sealed with QoreSeal to every member's ML-KEM-1024 key. The envelope's hash is on chain in an `EnvelopeGranted` event |
| Registered recipient keys | The chair's browser reads each director's key from QoreChain's registry with `qor_getKEMKey`. Our server is never asked whose key is whose |
| ML-DSA key binding | The registry accepts a change only when `pqcKeyStatus` returns a registered ML-DSA-87 key with possession proven for the chair, and `pqcVerify` accepts the signature against it |
| Client-side encryption and decryption | Both happen in the browser. Our server and store hold ciphertext, named by its SHA-256 |
| Key rotation and earlier data | Removing a director and changing the key are one transaction. The ledger works out who can open which pack from epochs, never from dates |

## From a terminal

With no account and no secret. The attack suite uses the shared library and the server package, so those two are installed first:

```bash
git clone https://github.com/ramakrishnanhulk20/ava
cd ava/packages/core && npm install
cd ../server && npm install
cd ../../security && npm install
npx tsx run.ts --offline
# 4 of 4 offline attacks held.
```

The live attack suite, its last run and the contract's own prove script are described in [Getting started](/docs/getting-started) and [Security](/docs/security).
