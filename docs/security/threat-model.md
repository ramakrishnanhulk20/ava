# Threat model: the quantum-safe board room

Written 16 Nov 2026 at the architecture gate, before any contract code, from a plain functional
description of the system. Sections A, B and C come from a pre-implementation design review. Section
C is the definition of done: the build is complete only when every invariant in it is shown to hold,
and each one has an attack script in `security/` that tries to break it on testnet.

Platform facts are linked to QoreChain's documentation. This file is kept current as the code lands.

## 0. Design gaps found in review, and how the design answers them

| # | Gap | Answer in the design |
|---|---|---|
| 1 | A relayer window can list at most 16 contracts, so one registry per board breaks at board 16, and an unscoped fallback lets a leaked relayer key call anything | One `BoardRegistry` contract holds every board. The relayer's window lists that one address (C25) |
| 2 | Envelopes are unsigned and only document ciphertext was hash-checked, so a substituted envelope could hand the chair or the bot an attacker-known epoch key | Every envelope's SHA-256 is recorded on chain and checked before it is opened or resealed (C12) |
| 3 | One envelope per epoch cannot represent a member who joins mid-epoch | Append-only list of envelopes per epoch (C6), each checked by the ledger (C39) |
| 4 | The demo bot admitted any address | The guest signs a fresh bot challenge with its own registered ML-DSA key first; one admission per address; demo cap, with guests removed in the background and never inside a join (C33, C34, C41) |
| 5 | Recipient KEM keys reached the chair only through our server | Browsers read KEM keys directly from the public EVM JSON-RPC with `qor_getKEMKey`. Probed live on 16 Nov from two unrelated origins: it answers browsers. Our server is never on that path (C15) |
| 6 | Native-lane registrations need POST to a REST endpoint that sends no CORS headers | The proxy accepts POST only for transaction simulate and broadcast, with a body cap sized to one registration (C22). Probed 16 Nov: REST and the consensus RPC refuse browsers directly |
| 7 | Once-only, rate, budget and nonce decisions need shared durable state | A small shared key-value store; nothing security-relevant lives in process memory (C31) |
| 8 | Public blobs served from the app's origin could run as the app | Blobs come from a separate origin as `application/octet-stream`, attachment, `nosniff`, sandbox CSP (C29) |

Resolved open questions: identities are unified accounts (coin type 60), so the `qor1` and `0x` forms
are the same 20 bytes (C16). A native-lane transaction as the drill proof is still to be confirmed
with the organisers; C36 covers both cases.

## A) App-class risk profile

In security terms this product is nine systems at once:
1. An end-to-end encrypted document store shared by many tenants. Each board is a tenant. Our server, the blob store and the chain are not trusted with confidentiality. Confidentiality rests on keys held in browsers, on how those keys are handed out, and on the order in which on-chain actions land.
2. A browser wallet. Every user's master secret (the 24-word mnemonic, from which all three keys derive) lives in web storage on our origin.
3. A contract whose authority comes from off-chain signatures (meta-transactions). Anyone may submit; only the chair's ML-DSA-87 signature counts.
4. A service that spends its own money for anonymous callers. The relayer pays gas and the sponsor pays QOR.
5. A server-side signing oracle. The demo chair bot signs with a privileged key when an anonymous visitor asks.
6. A request forwarder to a fixed upstream (the REST proxy).
7. A file host with anonymous uploads and public reads (the blob store).
8. A service that renders content controlled by other tenants: decrypted documents, and strings read from chain.
9. A security claim built from public events. The exposure ledger's correctness is itself a product promise.

The categories that typically bite these classes, tied to the flow where each one bites here:

A1. Forged, replayed or reused authorization. Flow: every registry function. Any account may submit, so the chair's signature is the only gate. It fails if the signed message misses a parameter, the nonce, the registry address or the chain id, or if the browser and the contract encode the message differently. It also fails if the bytes could be read as something else the same ML-DSA key signs: the chair's key is its account key, which also signs native-lane transactions. The Q-Day Drill bot will replay every signature it can find on chain.

A2. Misuse of cryptography and key distribution. Flows: add member, remove member, read document. Four weak points:
- The chair seals to ML-KEM keys it reads from somewhere.
- Envelopes are unsigned and fetched from a public store ([QoreSeal docs](https://docs.qorechain.io/developer-tools/qoreseal)).
- Several chair devices can encrypt under one epoch key, so AES-GCM nonces can repeat.
- AAD and purpose strings built in two places can differ.
Each one either gives an outsider the epoch key or breaks decryption.

A3. Races and ordering (the check happens at one time, the use at another). Flows: a document post and a member removal racing through the relayer; two chair sessions rotating from different views of the member set; parallel guest joins; parallel sponsor requests for one address. On a board, ordering protects confidentiality: a document that lands after a removal, under the old epoch key, is readable by the director who was removed.

A4. Script injection and key theft in the browser (cross-site scripting). Flows: open a document, list my boards, the exposure ledger, blob downloads. Any script on our origin can read every stored identity and capture the passphrase as it is typed. Inputs that reach the page: decrypted documents written by another tenant's chair, chain strings (URIs, ids, event data), proxy responses, and blobs if they are served from our origin.

A5. Server-side request forgery and open proxy. Flow: the REST proxy. A path joined onto a base URL can change the host (`//evil.example/` or a full URL), and a redirect the server follows can land anywhere the server can reach. Separately, the public REST rate-limits each IP. Every user shares our server's quota, so one heavy client can use it up for everyone.

A6. Draining money and resources. Flows: sponsor, relay, upload, guest join. Each anonymous request spends something: QOR, gas, window slots that renew themselves, storage, member slots, envelope bytes (1,632 per recipient in mlkem mode).

A7. Confused deputy and signing oracle. Flows: the demo chair bot and the relayer. The bot signs with a key that becomes the demo chair account's only protection once the drill key is published. The relayer submits to whatever target the request names.

A8. Handling of secrets. Flows: relayer, sponsor, bot. The server holds both keys of two funded accounts and the ML-DSA key of a third. In Next.js, a value under a `NEXT_PUBLIC_` name, or one passed to a client component, ships to every visitor.

A9. Unrestricted upload. Flow: blob upload. Naming blobs by their hash only helps if the server computes the hash. Public read makes the store a free host for anything.

A10. Integrity of a derived claim. Flow: the exposure ledger. It understates exposure if it is built from timestamps instead of epoch grants, if it reads a look-alike registry or a log read that was cut short, or if it trusts events about who an envelope was sealed to without checking the envelope.

A11. Identity confusion. Flows: invite and add, sponsor, guest join, KEM lookup. One account has a `qor1` form and a `0x` form, and the KEM route accepts both. If two parts of the system convert between them differently, the chair adds one account and seals to another.

A12. Contract basics. Two apply. Gas and storage griefing (member set size, URI length). An inactive precompile that answers with empty data instead of reverting ([EVM precompiles](https://docs.qorechain.io/developer-guide/evm-precompiles)). Front-running applies only as copying: a copied relayed action has the effect the chair intended, and the relayer pays for its own reverted duplicate.

Do not apply, and why:
- SQL or NoSQL injection: no database is described. If one is added for the shared state in C31, its queries are parameterized.
- OS command injection, server-side template injection, XML external entities: no shell, no server-rendered user templates, no XML.
- Session hijacking and cross-site request forgery: there are no cookies or sessions, and every authority is a signature over one specific action. Cross-origin access still matters (C23), because any web page could make its visitors' browsers call an endpoint that spends money.
- Reading someone else's object by guessing its id: everything stored is public by design and protected by encryption, so fetching another tenant's object yields only ciphertext.
- Reentrancy, price-oracle manipulation, flash loans, token approval abuse: the contracts hold no value, price nothing, send nothing, and call nothing untrusted. Their only outside calls are static calls to the two PQC precompiles.
- DNS rebinding: the proxy's host is one fixed HTTPS name and no attacker-chosen name is ever resolved, as long as C22 holds.

## B) Threat model

### Trust boundaries
- T1. Browser to our endpoints (relay, sponsor, proxy, upload, guest join): every field, header and request rate is untrusted.
- T2. Any EVM sender to the registry: calldata is untrusted. Authority comes only from pqcVerify against the chair's registered key.
- T3. Registry to the PQC precompiles: trusted chain code, but an inactive precompile returns success with empty data.
- T4. Our server to the public REST and EVM RPC: trusted for chain state over HTTPS. For native-lane reads that browsers cannot make directly, our server sits between that state and the browser.
- T5. Blob store to readers (browsers and the bot): bytes are untrusted until their SHA-256 matches the on-chain record.
- T6. Chain state to the app: trusted as a record of what happened, but much of it is written by attackers. Anyone can deploy a contract with our ABI and events, register a KEM key, create a board and add any address to it.
- T7. One tenant to another: a chair's signed URIs, sizes, ids and document plaintext are untrusted for that board's directors. Those directors may sit on other boards whose keys live in the same browser storage.
- T8. Browser storage to the app: the stored identity blob is read back and must pass authentication when it is decrypted.
- T9. Out-of-band channels: the director's address passed to the chair, invite links, board addresses in app URLs.
- T10. Server secrets to anything that leaves the server: responses, logs, error pages, client bundles, server-component payloads.
- T11. The Q-Day Drill: from 18 Nov an outside party holds the demo chair's secp256k1 key, and after the drill so does everyone.
- T12. Relay responses to the browser: a transaction hash is a claim, not a result.
- T13. npm dependencies to the browser bundle: every package runs on our origin, next to the keys.

### Attacker-controlled inputs
Direct:
- Relay: the action type, the target, every parameter (member address, envelope hash, URI, document id, epoch, ciphertext hash, byte size, add mode), the nonce, the deadline, the signature bytes, the body size, the request rate, and headers such as X-Forwarded-For.
- Sponsor: the address string (prefix, checksum, case, length, 0x or qor1, contract or module addresses), how often it is sent, and how many different addresses are used.
- Proxy: path, query string, percent-encoding, dot segments, method, headers.
- Upload: the bytes, their length, the declared content type, any key or name the client suggests.
- Guest join: the guest address, any proof offered, the request rate, the number of identities.
- App URLs and invite links: registry addresses, board ids and chair addresses.

Indirect:
- Upstream REST and RPC responses: status, headers, redirects, body size, latency, `found` flags, key bytes, the address echoed in a KEM record, and log pagination that stops early.
- Chain content written by others: look-alike registries and their events, the KEM keys members choose, PQ key records, transaction memos, and any board names or labels if they are added later.
- Blob contents as served, and whatever an on-chain URI points to.
- Chair-signed values as a director sees them: URI, byte size, id, and the decrypted document with its declared name and type.
- Values stored and read back later: the encrypted identity in browser storage, cached epoch keys in the browser and in the bot, the server's records of sponsored addresses, rate counters, nonce queues.
- Time: the block timestamp (set by validators) and the browser clock used for deadlines.
- Keys others hold: from 18 Nov the drill bot can make valid secp256k1 signatures for the demo chair account, and after the drill anyone can.
- The mempool: relayed actions can be seen and copied before they land.

### Privileged position and assets
- The relayer account's two keys, its QOR, and its open EVM window. The window is a budget of transactions and QOR that its classical key can spend with no further post-quantum signature.
- The sponsor account's two keys and its QOR.
- The demo chair's ML-DSA-87 secret key, plus its ML-KEM key or cached epoch keys. Once the drill publishes the secp256k1 key, this one server secret is the demo chair account's entire protection. With both keys, an attacker can sign native-lane transactions, open windows and rotate the key.
- Our origin: every user's encrypted identity sits there and every passphrase is typed there. Script running on our origin reaches every board those users belong to.
- Our server's network position: its IP's quota at the public REST, and anything its runtime can reach.
- The blob store's write path, and the domain it serves from.
- The power to spend money: sponsor transfers, relayer gas, automatic window renewal.
- The registry: the source of truth for "is this a real board".
- Within each board: the chair's ML-DSA key, which controls membership and epochs, and every director's browser, which holds every epoch key sealed to that director.

### Attacker goals
- G1. Read documents of a board they are not on, or were removed from. Flows:
  - (a) swap a member's ML-KEM key during add or remove member;
  - (b) swap the current epoch envelope so the chair's browser or the bot encrypts or reseals under a key the attacker knows;
  - (c) run script on our origin through a malicious document, a chain string or a blob, and read the stored identity;
  - (d) get a document posted under epoch E to land after a removal that moved the board to E+1;
  - (e) race two rotations so the newer epoch is sealed from a stale member list that still includes the removed director.
- G2. Act as the chair. Flows: replay an action that already landed; reuse a signature on another board, another chain or after a redeploy; find a parameter the signature does not cover; get the chair's key to sign bytes that are also a valid app action, or the reverse; make the demo bot sign for them; steal the server's demo ML-DSA key and pair it with the published drill key; find any endpoint or contract role that trusts a secp256k1 signature or msg.sender.
- G3. Spend our money. Flows: script thousands of identities against the sponsor; send the relayer actions that will revert, or copy its pending actions so its own copies revert; push actions with high gas; ride the automatic window renewal; on 18 Nov, use the drill key inside any window the demo chair account has open.
- G4. Make the exposure ledger lie. Flows: deploy a look-alike registry; cut a log read short; exploit a calculation by timestamp that misses seal-current grants; seal an epoch key to a non-member in an envelope the ledger never inspects; add strangers to the demo board so the ledger says they read its documents.
- G5. Take the demo down while judges are using it. Flows: mass guest joins that pass the member cap, QoreSeal's 1,024-recipient cap or the upload cap; contention in the bot's and the relayer's nonce queues; using up our server's upstream REST quota through the proxy; filling the blob store.

## C) Defensive-programming standards (the definition of done)

Each invariant below is an outcome. Any change that touches an area names the invariants it carries,
and review checks the file and function that upholds each one. The attack scripts in `security/` try
to break each one on testnet and save the output.

Note on the chosen shape: the review was written against a factory with one registry per board. The
design now uses one `BoardRegistry` for every board (gap 1). Read "factory" below as that registry,
"isRegistry" as "the board id exists in it", and "registry address" as "registry address plus board id".

### C.1 Board authority
- C1. Only the chair's current, possession-proven ML-DSA-87 key can change a board. Every state-changing function succeeds only when pqcVerify returns true for a message the contract builds itself. The key comes from pqcKeyStatus(chair) and must have registered true, algorithmId 1, possessionProven true, and length 2,592 bytes. msg.sender grants nothing. An inactive precompile, empty return data or a decode failure reverts. Proof: call each function with no signature, with another account's valid signature, and with a chair whose possessionProven is false. All revert.
  - Fail-closed outcome: if the chair's key ever stops being a possession-proven ML-DSA-87 key (the chain replaces or removes it), every write to that board reverts for good and the board is frozen. That is the intended result. A board nobody can prove authority over changes for nobody, and its past documents stay readable to the members who already hold the keys.
  - Upheld by: `packages/contracts/src/BoardRegistry.sol` `_authorise` and `_provenKey`.
- C2. One signature authorizes one action, once, in one place.
  - The signed message covers: an app domain tag, block.chainid, the contract's own address, the board id, the action code, every parameter that reaches storage or an event (including the add mode and the expected new epoch number), the nonce and the deadline.
  - Nonce: one per board, shared by every action type (per chair for board creation). Strictly sequential: it must equal the stored value, then it goes up by one.
  - Deadline: in seconds, checked against block.timestamp, and never more than one hour ahead, so no signature outlives a testnet reset that redeploys at the same address.
  - Replay protection never keys on signature bytes, because ML-DSA allows many valid signatures for one message.
  - Proof: replay a landed action; submit board A's signature to board B; change each parameter in turn; use an expired deadline and one too far ahead. All revert.
  - No signature from the app's own signers outlives one hour past the latest block. The contract only checks the deadline when the action lands, so a signature made with a deadline a year ahead would be valid in its last hour. The signing functions therefore take the latest block's timestamp and refuse any deadline at or before it, or more than MAX_DEADLINE_AHEAD (3,600 seconds) after it.
  - Any change to who may sign for a board moves that board's nonce in the same transaction. The message does not name the signer (except for board creation), so a new chair's first signature must not be able to match an old chair's unused one.
  - Upheld by: `packages/core/src/sign.ts` `signBoardAction` and `signChallenge` (the window check); `packages/contracts/src/BoardRegistry.sol` `transferChair` (nonce plus one) and `_checkDeadline`.
- C3. App signatures can never be anything else. Every Ava message is a fixed length: 256 bytes for a board action, 224 for a guest challenge. Its domain tag is not valid UTF-8 inside its own 32 bytes, so it can never be read as the text of a reserved prefix. And its first four bytes, read as a big-endian length, are larger than the whole message, so it can never be read as a length-prefixed message that is shorter than it is. The old rule, "the tag does not start with q", was wrong: the chain's legacy hybrid v1 sign bytes start with a four-byte length (first byte 0x00), and the challenge tag also starts with 0x00. The rule above holds for every form the pinned SDK builds (hybrid v1 and v2, proof of possession, key rotation, migration v1 and v2), and `signAction` refuses to sign any of them.
  - Upheld by: `security/attacks/offline.ts` attack `C3-v1-framing` (builds every sign-bytes form in the pinned SDK and checks each one); `packages/core/src/sign.ts` `signAction` (signs only 256 or 224 bytes under the right tag).
- C4. The browser and the contract sign and verify the same bytes. One specification builds the message:
  - abi.encode, never abi.encodePacked over two or more variable-length values;
  - parameters committed as a hash, so the message has a fixed length;
  - pure ML-DSA-87 with an empty context and no prehash, which is how pqcVerify checks it;
  - total pqcVerify input under the 16,384-byte precompile limit ([EVM window reference](https://docs.qorechain.io/developer-guide/evm-window-reference)).
  Proof: one shared test vector that the Solidity tests and the TypeScript tests both produce, byte for byte.
  - Upheld by: `packages/core/src/actions.ts` `actionMessage` and the six `params` functions, and `packages/contracts/src/BoardRegistry.sol` `_message` with the same six. One file of vectors, `packages/core/test-vectors/actions.json`, is written by `packages/core/scripts/vectors.ts` from the TypeScript builders and read by `packages/contracts/test/BoardRegistryVectors.t.sol`, where the contract must build the same 256 bytes. A third implementation, `packages/core/crosscheck/check_actions.py`, rebuilds every vector from `docs/spec/actions.md` in Python with its own Keccak-256 and shares no code with the other two (27 of 27 checks, and it fails on a tampered vector). Live attack: `C4-same-bytes`. What it does not cover: a second implementation of the signature check or of the encryption, which rest on QoreChain's and the platform's own libraries.
- C5. A document is always posted under the epoch that is current when it lands. postDocument reverts unless its signed epoch equals the board's epoch at execution. removeMember and rotateEpoch set the epoch to exactly the old value plus one, and the signature names that number. Proof: sign postDocument for epoch E, land a removeMember first, then submit the postDocument. It reverts.
  - Upheld by: `packages/contracts/src/BoardRegistry.sol` `postDocument`, which reverts `WrongEpoch` unless the signed epoch is the board's epoch when it lands, and `_checkNextEpoch`, which `removeMember`, `rotateEpoch` and a rotating `addMember` all pass through. Live attack: `C5-old-epoch`.
- C6. History is append-only. A document id is assigned once (by the registry, or checked as unused) and its record never changes. Every envelope that ever granted an epoch's key stays on chain in an append-only list for that epoch: a seal-current addMember appends and never replaces. Every change emits an event with enough fields (member, epoch, envelope hash, mode, nonce) to rebuild the full state from events alone.
  - Upheld by: `packages/contracts/src/BoardRegistry.sol`: `postDocument` refuses a used reference (`DocRefUsed`) and no function rewrites a stored document; each epoch's grants are a list that only grows (`getGrants`); every write emits its event with the board's nonce. Live attack: `C6-append`. The web app rebuilds a board's members from events alone and compares them with the registry's list on every read (C38).
- C7. A board is always well formed. The chair is always a member and cannot be removed. Members are unique. The member count stays between 1 and MAX_MEMBERS, which is at most QoreSeal's 1,024-recipient cap and low enough to keep every function well inside the gas limit. Adding an existing member or removing a non-member reverts. The target of transferChair must be a current member whose key is possession-proven at that moment. If the chair's key later stops being a possession-proven ML-DSA-87 key, the board is frozen for good (C1); that is the fail-closed outcome, not a bug.
  - Upheld by: `packages/contracts/src/BoardRegistry.sol` `addMember`, `removeMember`, `transferChair` and `_provenKey`.
- C8. Storage and gas are bounded. Every variable-length parameter has an on-chain length cap, and no function loops over a set without a fixed upper bound.
  - Upheld by: `packages/contracts/src/BoardRegistry.sol` `MAX_MEMBERS` (64), `MAX_ENVELOPE_SIZE` (110,000 bytes), `MAX_CIPHER_SIZE` (25 MiB) and the checks that enforce them (`BoardFull`, `_checkEnvelope`, `BadCipherSize`). Hashes and sizes are stored, never the blobs. Live attack: `C8-oversize`. Fuzz and invariant tests are in `packages/contracts/test`.
- C9. Real boards are the ones the registry made. The registry answers whether a board id exists. Every client and server treats any other contract address or board id as unknown, whatever its ABI and events look like. The server also refuses to relay anything until the code at the registry address hashes to the build that was deployed. An address with no code answers every `eth_call` with success, so the pre-flight alone would not notice.
  - Upheld by: `packages/server/src/relay.ts` `registryChecked` (answers 503 `registry_mismatch` before any counter moves) and `packages/server/src/config.ts` `REGISTRY_CODE_KECCAK`.
- C10. There is nothing to drain and no classical owner. The contracts accept no value (non-payable, no receive or fallback function) and hold no tokens. Non-payable does not stop value being forced in (a native send from a self-destructing contract can still land a balance), so the promise is that the registry holds no value it can move: nothing in it reads its balance or sends anything. No role is checked against msg.sender: no Ownable owner, no admin, no upgrade key held by a secp256k1 account. If anything is upgradeable, upgrades go through the same ML-DSA-signed path.
  - Upheld by: `packages/contracts/src/BoardRegistry.sol` as a whole. It has no payable function, no receive or fallback function, and nothing in it reads or sends its balance.

### C.2 Encryption and key distribution
- C11. Epoch keys are fresh. Each one is 32 bytes from the platform's cryptographic random source, new for every epoch, never derived from an earlier key, and never shared between boards.
  - Upheld by: `packages/core/src/seal.ts` `newEpochKey`, the only place an epoch key is made: 32 bytes from the platform's random source, refused if all zero, and typed so that only `sealEpochKey` accepts it. `packages/web/lib/chair/board.ts` calls it once for a new board and once for each rotation. Test: `packages/core/test/seal.test.ts` "are 32 fresh, non-zero random bytes each time". What it does not cover: a device whose random source is broken.
- C12. Nothing is used until its hash matches the chain. No envelope is opened, no epoch key is used to encrypt or reseal, and no ciphertext is decrypted unless the SHA-256 of the exact bytes received equals the on-chain record for that board and that epoch or document.
  - The hash is taken over raw bytes, in the same form that was uploaded and recorded. Never the `qoreseal:` text form, never a re-encoding.
  - The epoch number inside the opened key payload must equal the expected epoch.
  - This applies to the chair's browser and to the bot, not only to readers.
  - The same rule covers keys the device makes itself. A device encrypts, or reseals, under epoch E only with a key it opened from an envelope whose hash is in `getGrants(board, E)`. A key it generated for an action that then reverted is never used afterwards. Otherwise two chair sessions at the same epoch could each seal a different new key, only one action lands, and the other session's key (sealed to a member who was just removed) could be used to encrypt a later document that the removed member can read.
  - Upheld by: `packages/core/src/seal.ts` `openEpochKey` (returns the only key type `OpenedEpochKey` that `encryptDocument` accepts) and `newEpochKey` (returns `FreshEpochKey`, which `encryptDocument` refuses and `sealEpochKey` accepts).
  - What that proves, and what it does not: an `OpenedEpochKey` proves the key came out of an envelope that passed `openEpochKey`'s size and SHA-256 checks against the hash the caller passed in. It does not prove that hash is the one the chain lists. Checking the hash against `getGrants(board, E)`, read at the block the app is working from, belongs to the web app, which is not built yet. Until it is, this rule is only half enforced in code.
- C13. Every ciphertext is bound to its place.
  - QoreSeal's chainId is `qorechain-diana`. Its purpose string is built by one function from the board's place (SHA-256 of the registry address and the board's random boardRef) and the epoch number, within QoreSeal's allowed characters and 128-character limit.
  - The document AAD is one fixed binary layout (place, epoch, docRef), built by one function for both encryption and decryption. The board's sequential id is never used in encryption, because the first envelope is sealed before the id exists.
  - An envelope or ciphertext moved to another board, epoch or document fails to open. Proof: move each one across boards and epochs; every attempt gives DECRYPTION_FAILED or a GCM failure.
  - Upheld by: `packages/core/src/seal.ts` `placeOf` and `purposeFor` (the one builder of QoreSeal's purpose string), `sealEpochKey` and `openEpochKey`, and the one builder of the document's additional data, used by both `encryptDocument` and `decryptDocument`. Tests: `packages/core/test/seal.test.ts` "opening with the wrong epoch, board or registry fails (C13)", "an envelope moved between two boards the same chair created fails to open" and "decrypt with a moved docRef, epoch, board or registry fails (C13)". Live attack: `C13-move`. The byte layout is in `docs/spec/pack.md`.
- C14. No key and nonce pair is ever used twice. Each document is encrypted under its own key, derived with HKDF from the epoch key with the document's random docRef as salt (because several chair devices may share one epoch key), with a fresh random 96-bit GCM nonce.
  - Upheld by: `packages/core/src/seal.ts` `documentKey` (HKDF-SHA-256, the epoch key as input, the pack's own random `docRef` from `newDocRef` as salt) and `encryptDocument` (a fresh random 12-byte nonce for every call). Test: `packages/core/test/seal.test.ts` "follows the spec layout: HKDF salt docRef, info ava-doc-v1 || place || epoch, AAD place || epoch || docRef". What it does not cover: a device whose random source repeats.
- C15. Every recipient key is genuine. An ML-KEM key is used for sealing only if all of these hold:
  - it is the key registered for exactly the 20-byte address being sealed to (the address in the response, decoded by the C16 codec, equals the address requested);
  - its algorithm id is 2, it is 1,568 bytes, and it passes validateMlkemPublicKey;
  - it did not come from a server we run. The browser reads it from the chain with `qor_getKEMKey` on the public EVM JSON-RPC ([key features](https://docs.qorechain.io/introduction/key-features)), which answers browsers directly (probed 16 Nov).
  A `found: false`, a mismatch or a timeout stops the seal.
  - Recipients come only from `fetchKemKey`, and it returns the account and its key as one pair (`KemRecipient`). The type brand sits on the pair, not on the key bytes, so a key cannot travel under another account's address without a cast. The sealing function accepts only that pair type.
  - One ML-KEM key, one member. A seal refuses one ML-KEM key listed under two accounts. The ledger's recipient-hint test (C39) cannot tell two accounts with one key apart, so the ledger shows an envelope with a shared key as unverified, never as clean.
  - What the chain does when a second account registers a key a first account already holds: it takes the copy. In the final attack run (19 Nov), `C15-shared-kem-guest` registered the seeded director Asha's published ML-KEM key as a fresh sponsored identity's own with `MsgRegisterKEMKey` (transaction `9CA46C7DB4C1568212709602EE3AAB67430E0634C08109D7F5328C2A72FF3154`, the fee paid by that identity), and `qor_getKEMKey` then answered that key for the identity. The KEM registry asks for no proof that the registrant holds the matching private key, and that is by design: QoreChain's KEM registry documentation says a published encryption key needs no proof of possession, because a KEM cannot sign and an account that publishes a key it cannot use only stops itself from receiving. What an app must not do is treat a published key as belonging to one account only. So the chain cannot be relied on to stop a copy, and nothing here depends on it: the app refuses to seal to or seat a key listed under two accounts. A copier cannot decrypt anything sealed to the copied key, because it does not hold the private half. In the same run the demo bot refused the copier's join 403 `key_shared`, and board 15's members and nonce did not move (C42).
  - Upheld by: `packages/core/src/kem.ts` `fetchKemKey`; `packages/core/src/seal.ts` `sealEpochKey`. The pair brand is a compile-time check, covered by a `@ts-expect-error` case in `packages/core/test/`.
- C16. One account, one form. A member is a 20-byte value. Addresses that arrive in a request are decoded strictly (qor1 with a valid checksum, or 0x in exact EIP-55 form); the lenient decoder that also accepts all-lowercase 0x is used only for values read from the chain. Every component (browser, relayer, bot, sponsor, ledger, KEM lookup, pqcKeyStatus) converts between `qor1` and `0x` with one shared function and compares bytes, never strings. Anything that does not decode with a valid checksum is rejected. Identities are unified accounts (coin type 60), so the address a new identity shows the chair is the one whose 20 bytes own its ML-DSA and ML-KEM registrations. Proof: onboard an identity, add it by its `0x` form, and confirm that pqcKeyStatus and the KEM lookup both find it.
  - One recovery phrase gives one account and one key set. A phrase pasted with a no-break space, an ideographic space, a double space or full-width letters is the same phrase. One function, `canonicalPhrase` (Unicode NFKD, trimmed, split on any whitespace, joined with single spaces, exactly 24 words with a valid checksum), normalises it, and only its output reaches any key derivation, in the browser and on the server. Before this rule, the SDK hashed the raw string into the ML-DSA-87 seed, so a pasted variant gave the right address and a different signing key.
  - Upheld by: `packages/core/src/identity.ts` `canonicalPhrase` and `identityFromMnemonic`; `packages/server/src/chain/account.ts` `normalizeMnemonic`; attack `C16-phrase` in `security/attacks/offline.ts`.
- C17. A rotation is sealed to exactly the members the registry holds once it lands. The browser reads the member set and the nonce from the same block and signs that nonce. Because every action moves the nonce (C2), a rotation built from a stale view reverts instead of reaching a removed director. Proof: two chair sessions remove two different members at the same time. The second one reverts, and the first removed member's key cannot open the new epoch's envelope (NOT_A_RECIPIENT).
  - Upheld by: `packages/web/lib/guest/board.ts` `readBoard`, which reads the record, the nonce and the member list at one block; `packages/web/lib/chair/recipients.ts` `rotationRecipients`, which works out who the new key is sealed to from that list; and `packages/web/lib/chair/board.ts` `addDirector` and `removeDirector`, which sign that same nonce. The demo bot does the same in `packages/server/src/demo.ts`. Tests: `packages/web/lib/chair/recipients.test.ts`. Live attack: `C17-concurrent`.

### C.3 Browser keys and rendering
- C18. Secrets stay in the browser that made them. The mnemonic, the ML-DSA and ML-KEM secret keys, epoch keys and the passphrase are never sent to any server, never logged, never put in a URL or an analytics event, and never written to storage unencrypted. The stored identity is encrypted with AES-GCM under a key from a slow password KDF with a fixed minimum cost (PBKDF2-SHA-256 at 600,000 iterations or more, or scrypt, or Argon2id), a random salt and a minimum passphrase length. A failed or malformed decryption leaves the wallet locked. There is no fallback.
  - Upheld by: `packages/web/lib/guest/vault.ts` `sealPhrase` and `openVault` (PBKDF2-SHA-256 at 600,000 rounds, AES-256-GCM with a fresh salt and nonce, a 10-character minimum, and a stored record that is checked for shape and cost before any key is derived) and `packages/web/lib/guest/identity.ts` `createGuest`, `openGuest` and `protectStoredPhrase` (the vault is the only thing ever written; the open identity lives in memory for one page view, and a reload asks for the passphrase again). Tests: `vault.test.ts` and `identity.test.ts` in the same folder. What it does not cover: a passphrase weak enough to guess offline, and a device that is already compromised while the vault is open.
- C19. No script but ours runs on the app's origin. The Content-Security-Policy is nonce-based, with no unsafe-inline or unsafe-eval for scripts, and sets object-src none, base-uri none and frame-ancestors none. There is no dangerouslySetInnerHTML, or anything like it, with chain data, document data or upstream responses. Every chain string, id, URI and error message is rendered as text.
  - Upheld by: `packages/web/proxy.ts` `proxy`, which serves every page with the policy `packages/web/lib/csp.ts` `contentSecurityPolicy` builds around a nonce `freshNonce` makes for that one response (18 random bytes). `script-src` is `'self'`, the nonce and `'strict-dynamic'`, so no host is trusted for scripts and nothing inline or evaluated runs. `default-src`, `object-src`, `base-uri`, `form-action` and `frame-ancestors` are `'none'`. `connect-src` names our origin, the chain's public EVM endpoint, the blob store's origin and the storage API's upload path, and nothing else. The only frame allowed is a `blob:` one, used for C20. `packages/web/app/layout.tsx` waits for the request (`connection()`), so no page is built ahead of time without a nonce. The blob origin comes from an environment variable and is used only if it is one bare https origin, so a bad value cannot add a directive. Tests: `packages/web/lib/csp.test.ts` pins the production policy word for word, the refusal of a short or malformed nonce and of nine bad origins, and scans the app's source for `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `document.write`, `srcDoc` and `javascript:` (none). Live, 23 Nov: a production build served with this policy was walked end to end (every page, and on board 47 a create, four posts, every pack opened by two identities, an add, a remove, the envelope check and a restore from recovery words) with no violation reported by the browser. What it does not cover: style attributes stay allowed (`style-src-attr 'unsafe-inline'`), because the server renders positions and motion as attributes, while a `<style>` element needs the nonce. The development server adds `'unsafe-eval'`, a socket and inline style for its own error overlay; production does not. And a policy does nothing against a deployment that is itself taken over and serves other scripts with a valid nonce.
- C20. A document from one board can never reach another board's keys. Decrypted content is never active content on the app's origin: it is never rendered there as HTML, SVG or XML, and never opened as a same-origin `blob:` URL of an active type. Previews run only in a sandboxed frame without allow-same-origin, for a short allowlist of types detected from the bytes (not from the declared type). Everything else downloads under a cleaned filename: no control characters, no bidirectional characters, no path parts. Proof: a chair posts an HTML file and an SVG that contain script. Opening them in a director's browser runs nothing on the app's origin.
  - Upheld by: `packages/web/lib/pack/format.ts` `kindOf`, which decides from the decrypted bytes alone and knows three answers: text, PNG or JPEG, and download. Markup, SVG and PDF are always a download, whatever the file was called. `packages/web/components/board/PackList.tsx` shows text as a text node, shows an image in `<iframe sandbox="">` from a `blob:` URL typed as that image, and hands everything else to the browser as `application/octet-stream` under the name `cleanFilename` leaves (no control or bidirectional characters, no path). Tests: `packages/web/lib/pack/format.test.ts`, and `csp.test.ts` checks that every frame in the app's source has an empty sandbox. Live, 23 Nov: on board 47 an HTML file carrying a script and an image with an error handler was posted and opened by the chair and by a director. It was offered as a download only, the page's title and a marker the script would have set were unchanged, and the browser reported nothing blocked because nothing was tried. An earlier run on board 42 did the same with an SVG. What it does not cover: what the user's own programs do with a file they chose to save.
- C21. Boards from strangers do nothing on their own. A board the user did not create or accept is labelled with its chair address and board id, and nothing in it is fetched or rendered until the user opens it.
  - Upheld by: `packages/web/components/board/BoardLobby.tsx`, which lists a board from two reads of the registry (`getBoard` and `isMember`, in `packages/web/lib/chair/summary.ts` `summariseBoards`) and shows its id, the account's standing and, for any board the account does not chair, the chair's full address. Opening a board reads its events and pack records from the chain (`packages/web/lib/chair/room.ts` `readRoom`). An envelope or a pack is downloaded only when the user presses open on a pack or runs the envelope check, and a pack's content is then handled as C20 says. Live, 23 Nov: a second identity added to board 47 saw it listed as a member, then as removed. Measured in that browser: the list and the opened board made requests to our origin and the chain only, and the first two requests to the blob store came when a pack was opened. What it does not cover: a chair can still add any address to a board, so a stranger's board can appear in the list. The list says so in plain words.

### C.4 Server endpoints
- C22. The proxy reaches only the chain's public REST, and only the parts of it the app needs.
  - The outgoing URL is parsed into a URL object, and that same object is the one sent. Its origin must be exactly `https://api-testnet.qore.host`.
  - The path must match one of the routes the app uses. Each path parameter is decoded by its own codec (address, hash, upgrade name), and query parameters are limited to the ones each route needs, with numeric caps.
  - Redirects are refused, not followed. No client header is forwarded.
  - The response goes back only as JSON, under our own `Content-Type: application/json` and `X-Content-Type-Options: nosniff`. Upstream headers are dropped, the body is capped, and there is a timeout.
  - POST is accepted only for transaction simulate and broadcast, with a body cap sized to one hybrid-signed registration.
  - Proof: `//evil.example/`, a full URL, `..%2f`, a double-encoded path and an upstream redirect all fail.
  - Upheld by: `packages/server/src/proxy.ts` `matchGetRoute` (a fixed list of routes, each parameter through its own strict codec), `upstreamUrl` (the upstream host is a constant, and a path is never parsed as a URL), `handleChainGet` and `handleChainPost`. Tests: `packages/server/test/proxy.test.ts`. Live attacks: the eleven `C22-` attacks, from `C22-double-slash` to `C22-protocol-features`. The upstream host itself is pinned by a unit test.
- C23. Our endpoints serve our app, not the internet. There is no wildcard CORS. Rate limits apply per client IP, as reported by the hosting platform (never a header the client supplies), and in total. They are set below the upstream per-IP budget, so no single client can spend that budget for everyone.
  - A request that a page on another site can make a browser send without a preflight (a beacon, an image, a form, a no-cors fetch) is refused before it counts against any limit, reads its body or reaches upstream. Every public handler first requires the header `x-ava: 1`, which such a request cannot carry, and refuses a `Sec-Fetch-Site` header that is anything but `same-origin`. Without this, visitors to a hostile page could spend every anonymous total on its owner's behalf. The envelope upload also accepts only `application/octet-stream`. The demo bot's own relay calls carry the header themselves.
  - An IPv6 client is counted per /64 and also per /48 at four times the per-IP limit, because one /48 holds 65,536 /64s. Every per-IP limit goes through one helper that applies this rule (`countClient`): the relay, the sponsor, the demo join and the limits behind `limit`. Every upload budget (document tokens, envelope uploads and their bytes) goes through `budgetKeys`, which counts the /64 and also the /48 at four times the budget, in both the check (`hasBudget`) and the spend (`spendBudget`). So ten /64s of one /48 get at most four times one client's tokens an hour, not ten times. No endpoint counts a client by its address alone.
  - One route sits outside these rules on purpose: `/api/search`, the docs search (`packages/web/app/api/search/route.ts`). It answers a GET from anywhere, because it reads only the published docs' own index: no secret, no store, no chain and nothing about a visitor. A query over 100 characters gets the empty answer without a search being run. We do not rate limit it; the host's own request limits apply.
  - Upheld by: `packages/server/src/http.ts` `refuseCrossSite`, called first in `packages/server/src/blob.ts` `handleUpload`, `packages/server/src/docupload.ts` `handleDocumentToken` and `handleDocumentVerify`, `packages/server/src/proxy.ts` `handleChainGet` and `handleChainPost`, `packages/server/src/relay.ts` `handleRelay`, `packages/server/src/sponsor.ts` `handleSponsor` and `packages/server/src/demo.ts` `handleDemoChallenge` and `handleDemoJoin`; `packages/server/src/ratelimit.ts` `countClient`, `limit`, `clientKey`, `budgetKeys`, `hasBudget` and `spendBudget`; `hasBudget` and `spendBudget` are called from `packages/server/src/docupload.ts` `handleDocumentToken` and `packages/server/src/blob.ts` `handleUpload`; `countClient` is called from `packages/server/src/relay.ts` `handleRelay`, `packages/server/src/sponsor.ts` `handleSponsor` and `packages/server/src/demo.ts` `handleDemoJoin`; attack `C23-cross-site` in `security/attacks/proxy.ts`.
- C24. The relayer pays only for valid actions on our own contract.
  - It builds the calldata itself from typed parameters.
  - The target is the one registry address, a build-time constant.
  - It broadcasts only after an eth_call of the exact transaction succeeds.
  - Gas limit and fee cap are fixed ceilings per action type.
  - It rate-limits per chair and per board. Past a daily spending ceiling it refuses actions and stops renewing its window.
  - It records the hash of every transaction it signs (send, window open, window close) under that transaction's nonce before it broadcasts. It keeps its own next nonce in shared state. That stored nonce moves forward only when our recorded hash at that nonce is seen on chain, and only by compare-and-set from the value read, never by an increment. Before any window open, close or send it compares the stored nonce with the chain's. If the chain is past it, every nonce in between must hold a transaction we recorded that is now in a block. If any one does not, someone else signed with the relayer key and the relayer halts, even when no window counter can see that transaction. A gap wider than 8 nonces halts too. One of ours still waiting for a block refuses for now and does not halt. A first run with nothing stored adopts the chain's value. It re-signs anything signed before a window renewal (opening a window moves the account nonce, [EVM window reference](https://docs.qorechain.io/developer-guide/evm-window-reference)).
  - Its day is 20 QOR in all. Public chair relays share 8 QOR of it, one chair address may use 1.5 QOR of that, and the demo bot has its own 12 QOR. A send reserves its worst case (gas ceiling times fee cap) on every ledger it touches before it broadcasts, or on none, and settles each reservation down to the receipt's real fee (gas used times effective gas price). With no receipt the worst case stays booked. Window opens and closes count on the total only. The booking is `sendLedgers` in `relay.ts`, which feeds `reserveOn` in `window.ts`; `settleSpend` settles it.
  - Upheld by: `packages/server/src/window.ts` `reserveOn`, `settleSpend`, `guardSend`, `checkNonce`, `oursSince`, `moveNonce`, `recorder` and `nonceKey`; `packages/server/src/relay.ts` `sendLedgers` and `handleRelay`; `packages/server/src/config.ts` `RELAYER_DAILY_CEILING_UQOR`, `CHAIRS_DAILY_CEILING_UQOR`, `DEMO_DAILY_CEILING_UQOR`, `PER_CHAIR_DAILY_UQOR`.
- C25. The relayer's window stays narrow. It is never unscoped in production. allowed_targets holds only the registry address. max_value is sized with evmWindowCost for a set number of actions, and renewal keeps the same scope. Proof: with only the relayer's secp256k1 key, try a QOR transfer, a call to any other contract and a contract creation. All are refused, and calls to our own contract carry no authority.
  - A suspected leak halts the relayer until an operator clears it. The signal is the chain's nonce for the relayer being past the one stored with a nonce in between that is not a transaction we signed, or a window spent outside our own recorded sends. The halt has no expiry; only `scripts/clear-relayer-halt.ts --confirm` ends it. The daily-ceiling refusal is different and ends at 00:00 UTC. On a halted day the relay still closes a live window it finds, and retries a close that failed, before it answers 503 `halted`.
  - Upheld by: `packages/server/src/window.ts` `haltAndClose`, `isHalted`, `clearHalt`, `checkNonce`, `oursSince` and `ensureWindow`; `packages/server/src/relay.ts` `relayOnce`; `packages/server/scripts/clear-relayer-halt.ts`.
- C26. A relay response is only a claim. The browser marks an action done only when the receipt shows success and the registry event for that very action is in the receipt, matched on board id and nonce. Never match on `EnvelopeGranted`: its nonce field holds the creation nonce for a new board and the board nonce for every other action, so a first board can emit two such events with the same board, epoch 0 and nonce 0. Until the receipt confirms, the screen says pending.
  - A signed action cannot be withdrawn. The nonce moves only when an action lands, so an action the chair gave up on can still land later, ahead of whatever the chair signed next at the same nonce (a later removal at that nonce would then revert). So "cancel" means landing a different action at that nonce, and the app never treats an action that has not landed as dead. Cancelling still works after a send the node refused: the in-flight mark gives way once the chain does not know the relayer transaction it names (C40), so the different action at that nonce is accepted instead of answering 409.
  - Upheld by: `packages/server/src/relay.ts` `handleRelay` (answers 202 with a hash and says nothing more) and `claimMark` (the mark that gives way). In the web app, `packages/web/lib/guest/join.ts` `confirmJoin` treats the hash the bot answers with as a claim: the receipt must show success and carry the registry's own `MemberAdded` event for this board and this account; `packages/web/lib/guest/leave.ts` `confirmLeave` asks the same of a guest's own removal, with `MemberRemoved`. A guest matches on its own address, because the nonce belongs to the bot's action, not the guest's. The chair's screens are not built yet.
- C27. The sponsor funds each new identity once, within a budget, with no more than it needs.
  - The address is decoded by the C16 codec.
  - The amount is a server constant, sized to the two registrations. A new account must register its key first ([first transaction](https://docs.qorechain.io/getting-started/first-transaction)), so a scripted identity is left with almost nothing.
  - Eligibility is read from chain: no registered PQ key, no balance.
  - A once-per-address record is written atomically to shared durable state before the send. It lives only as long as the request's lock until the send is about to start, then it is made permanent; a refusal before that point takes it back, so a refused address keeps its one chance. After a send that may have landed, the mark stays.
  - Per-IP and daily totals are capped, and sends are queued one at a time.
  - Upheld by: `packages/server/src/sponsor.ts` `handleSponsor` and `releaseMark`.
- C28. Every stored blob's name is the SHA-256 of the bytes the store actually holds, checked by the server, never a name the client chose. Envelopes are uploaded through the server, which hashes what it receives. Documents (too large for the host's request limit) go from the browser straight to the store under a short-lived token that allows exactly one pathname, `document/<sha256>`, octet-stream only, never overwriting, and exactly the size the request declared (1 byte to 25 MiB; any other size is 400 `bad_size`); the server then re-reads what the store holds, hashes it, and deletes it on any mismatch. An existing name is never overwritten. Byte caps are enforced while reading, not after buffering. Per-IP and total quotas apply. Issuing a token books its declared size on three daily byte budgets: 25 MiB per client a day (an IPv6 /48 shares four times that) and 1,250 MiB for everyone together, fifty times the per-client figure so that spending the total takes as many addresses as the hourly totals. A refused request books nothing on any of them. A token whose name is still empty 10 minutes after it was issued, plus a 1 hour grace, gives its bytes back once (`settleTokens` in the document sweep, up to 500 records a run, or `returnIfUnused` when a verify finds the name empty); the give-back is a single compare-and-set on the token's own record, so it cannot happen twice. Over any of them, the request is 429 `upload_bytes` and no token is issued. A kept document stays for good whoever sends the post, so these budgets bound how much the store can grow in a day, however a document is later posted. A document with no on-chain reference is deleted two hours after its upload, whether or not it was verified (C44). The verified mark holds the size the server read back, and `verifiedSize` is the only reader of it. The relay posts a document only when that verified size equals the signed cipherSize (C44), so a chair can no longer post a document it never verified by going through the relay. Calling the contract directly still can, so a posted blob with no verified mark is hashed once by the sweep: a match gets its verified mark, a mismatch is deleted and logged `document_mismatch_deleted`. A posted blob whose stored size differs from a cipherSize its posted mark records is deleted and logged `document_size_mismatch`. A blob the sweep cannot read is logged `document_read_failed` and kept, never deleted unhashed. One run hashes at most 200 MiB and starts no new read after 240 seconds, so what is left waits for the next run. The sweep keeps its place in the blob listing between runs (`docsweep:cursor`) and starts again from the first page after the last, so a flood of kept documents sorting ahead of a name cannot keep the sweep from ever reaching it. A listing the store refuses while a cursor is held resets the cursor to the start, so a cursor the store no longer accepts never stops the sweep.
  - Upheld by: `packages/server/src/docupload.ts` `handleDocumentToken`, `bookDocumentBytes`, `handleDocumentVerify`, `verifiedSize`, `sweepUnverified` and `moveListing`; `packages/server/src/config.ts` `DOC_BYTES_PER_CLIENT_DAY` and `DOC_BYTES_TOTAL_DAY`; `packages/server/src/blob.ts` `handleUpload`.
- C29. Blobs are served as plain bytes that cannot run. They come from a separate origin (another registrable domain, never the app's), as `application/octet-stream`, with `Content-Disposition: attachment` and `nosniff`. Checked live on 17 Nov: the store serves exactly these, plus `Content-Security-Policy: default-src 'none'`. It does not add a `sandbox` directive; the separate origin, attachment, octet-stream and nosniff together keep anything uploaded from running as the app, and the app never navigates to a blob, it only fetches bytes.
  - Upheld by: `packages/server/src/blob.ts` and `packages/server/src/docupload.ts`, which store every blob as `application/octet-stream` under its hash, with no random suffix and no overwrite, on the blob store's own domain. The serving headers are the store's. Live attack: `C29-headers`, which reads them back on every run. The web app never navigates to a blob URL: it downloads the bytes and handles them as C20 says.
- C30. Readers fetch only the expected location, and only as much as expected. The browser builds the fetch URL from the on-chain hash and the configured blob origin. An on-chain URI is used only if it equals that form when parsed by the same URL parser. Downloads stop at the on-chain byte size for documents, and at the largest possible envelope (56 + 1,632 x MAX_MEMBERS + payload) for envelopes. The size check comes before hashing.
  - Upheld by: `packages/web/lib/guest/board.ts` `blobUrl` (the URL is built from the on-chain hash and the configured origin, nothing else) and `readBlob` (no credentials, no redirects, stops as soon as more than the on-chain size arrives). The hash check follows in `openEpochKey` and `decryptDocument` before any key is used. On the server, `packages/server/src/blob.ts` `sameUrl`. Live attack: `C30-url`.
- C31. Every once-only, rate, budget and nonce decision lives in shared durable state or on chain, never in process memory. Serverless instances do not share memory, and a restart wipes it. Window renewal and the bot's queue run under a lock in that shared state, or on a schedule that exists between requests.
  - One rule for every once-only write whose false answer would refuse someone: it is checked by reading back the caller's own value before anyone is refused. The store's client retries a request whose reply was lost, so a write that did land can answer "no" the second time. `claimOnce` (`store.ts`) writes the value and, on a "no", reads the key back; a value equal to the caller's own counts as a yes, and every caller's value is its own alone (a random token, or a time no other caller shares). The shared-store lock does the same: `UpstashStore.withLock` reads its lock back after a "no". Uses: `takeAdmission` and `claimPass` in `demo.ts`, `sendOnce` in `sponsor.ts`, `claimMark` in `relay.ts`, `recordToken` and `retireToken` in `docupload.ts`, and the lock in `window.ts`.
  - Every give-back and settlement of a booking adds once. `addOnce` (`store.ts`) adds by compare-and-set from the value it read, under a lock every writer of that counter takes, and reads the key back after a refusal, so a write that landed with a lost reply is counted once and never twice. A write it cannot confirm leaves the amount booked, which overstates spend and never hides it. It is used by `giveBack`, `settleSpend` and `releaseSpend` in `window.ts`, and `giveBack` in `docupload.ts` for document bytes.
  - Upheld by: `packages/server/src/store.ts` `claimOnce` and `addOnce`; `packages/server/src/window.ts` `giveBack`, `settleSpend` and `releaseSpend`; `packages/server/src/docupload.ts` `giveBack`; `packages/server/src/demo.ts` `takeAdmission` and `claimPass`; `packages/server/src/sponsor.ts` `sendOnce`; `packages/server/src/relay.ts` `claimMark`; `packages/server/src/docupload.ts` `recordToken` and `retireToken`.
  - A cursor or counter that gates deletes moves only by compare-and-set from the value the run read, never by an increment, so a client retry that the store applied twice, or two overlapping runs, can never move it past a block nobody read. The same holds for the document sweep's listing cursor (`docupload.ts` `moveListing`) and for every counter that gates a removal or a halt: the relayer's stored nonce (`window.ts` `moveNonce`), the demo's run of unreadable key lookups (`demo.ts` `addUnreadableRun`) and the demo's hourly relay room (`relay.ts` `reserveDemoRelays`). ### C.5 Demo chair bot and the drill account
- C33. The bot is not a signing oracle. It builds every message itself and signs only three things, only for the configured demo board: addMember (admitting one guest), removeMember (a guest removal made by the scheduled sweep or the background pressure pass, never inside a join) and postDocument (the demo pack for an epoch that has no pack yet, built from the bot's own board read and its own fixed text, with nothing from any caller). It signs only after that guest has signed a fresh challenge the bot issued, using the guest's registered, possession-proven ML-DSA key. The challenge is bound to the demo board, a bot nonce and an expiry, under the C3 tag. The bot never signs bytes that came in a request. Every check a guest can fail runs before the bot counts, signs, uploads or relays anything for that guest, so a guest who will be refused costs nothing and takes no seat from anyone. A removal is made only by `sweepDemoGuests` and `freeDemoSeats`, each through `removeOneLocked`, and never by `handleDemoJoin`. The mirror of this rule on the client side is C45.

- C34. Admission is bounded. One admission per address. Per-IP and total rate limits. A demo member cap (DEMO_GUEST_CAP, 40) below MAX_MEMBERS, with guests removed in the background, so scripted joins can never reach QoreSeal's 1,024-recipient cap or the upload cap. Joins queue one at a time, because the board nonce is sequential.
  - The guest challenge is consumed by compare-and-set to a tombstone that carries the join's own token (`joinProven` in `demo.ts`), so a lost reply on that write never refuses a valid join: a read-back that finds this join's own tombstone counts as consumed by it.
  - A join is one add and never removes anyone. At a full board it answers 503 `board_full` (retry-after 30) before the challenge is used and before anything is counted: nothing against the guest, nothing from the day, the hour or the per-IP join count, and a background pressure pass is scheduled. The check reads a board size at most 5 seconds old (`boardFull`), so a flood of joins to a full board costs the chain one read every few seconds. The judge's retry reuses the same challenge. A board that fills between that check and the join lock answers the same way, but that join has already used its challenge (C43), so the web client asks for a fresh one after any `board_full`. After every admitted join that leaves the board above DEMO_GUEST_CAP minus DEMO_FREE_SEATS (34) members, a pass is scheduled too. See C41 for the pass itself.
  - Failed joins are capped per address: after the guest has proven its key, a refusal the guest caused counts against its address for that UTC day, and the sixth answers 429 `too_many_failures`. Only a 4xx other than 429 counts. A 5xx or a 429 is the service's own state and never counts, so a judge is not locked out for our trouble. A join takes from the day's 120 only once the bot is about to relay the admission.
  - The once-per-address admission mark is written when the join takes its lock and lives 150 seconds, the lock's lifetime, until `keepAdmission` makes it permanent just before the send. A join that stops with nothing sent takes it back (`settleMark`); if taking it back fails, it still ends within 150 seconds and never locks the guest out for good.

A mark whose add the chain does not know, or knows as reverted, while the guest is not a member, is released: `admissionStanding` finds it stale, `takeAdmission` frees it under the join lock, and `settleAdmissions` frees it in the scheduled sweep. A pending add keeps the mark and the guest gets 503 `admission_unsettled` (retry-after 30), with nothing counted against the guest. So does a mark whose standing cannot be read yet, and a mark a join still under way holds (it reads `<ms>:joining` until the add is signed), which means a second join of the same guest at the same moment is also told to retry. A guest the mark shows seated still gets 409 `already_admitted`. A join whose add was sent with no receipt seen is listed in a bounded list (`demo:unsettled`, at most 20 guests) for the sweep to settle. A write of the mark that landed but lost its reply reads back as this join's own value and is recognised as such; two joins of one guest can reach the admission mark (a second challenge issued after the first was consumed), the join lock serialises them, and their marks hold different values, so a read-back only ever matches the join that wrote it.
  - Every guest member has an admission time that the sweep acts on. A member with no record is dated from the block time of the latest `EnvelopeGranted` that names it, so every guest expires. The once-per-address mark is released only when a read of the board shows the guest is not a member. After a failure that follows a send (a revert, or a copy of the bot's `addMember` that landed first), the board is read again, and a guest who is a member keeps the mark and gets an admission time of now.

### C.6 Exposure ledger
- C38. The ledger never understates exposure.
  - It works from epoch grants, not timestamps. A person is exposed to every document of every epoch whose key was ever sealed to them, including documents posted earlier in an epoch they joined by seal-current.
  - It reads only the deployed registry, from the public EVM JSON-RPC, which answers browsers.
  - Any log read that fails, times out or is cut short shows "incomplete" instead of a shorter list.
  - The member set it rebuilds from events must match the registry's view functions at the block it read. A mismatch shows "incomplete".

- C39. The ledger checks the envelopes, not only the events. For each envelope on chain, it compares the recipient count in the header with the number of members whose ML-KEM keys match a recipient hint. Anyone holding a public key can run that test ([QoreSeal docs](https://docs.qorechain.io/developer-tools/qoreseal)). Any extra entry is shown as an unknown reader. Envelopes are therefore never sealed with `anonymous: true`. An envelope the ledger cannot check (for example, a member has since replaced their key) is shown as unverified, never as clean.

Tests: `packages/web/lib/chair/ledger.test.ts`. ### C.6b Added after the backend review (17 Nov)
- C40. Only work that can land consumes a signed party's budget, and every refusal a caller can cause runs before any shared counter. The relay runs its exact pre-flight before any per-chair, per-board or valid-action counter; requests that fail it count only against per-IP and a separate rejected total, so junk cannot starve a chair's real actions. A post whose verified size is missing or differs from its cipherSize is refused before anything moves (C44). The per-board, per-chair and valid-action counters move last, under the send lock, in the final step before the broadcast (`countAndRecord`): after the post bytes, the chair's own day, the shared shares, the second pre-flight, the nonce guard and the send cutoff have all passed, and just before the send record. A send that runs out of time before that step counts nothing. An action refused anywhere earlier, the cutoff included, takes none of them. They move once per action, whatever the retries: the first relay writes a mark named for the keccak256 of the calldata (`relay:counted:<calldata hash>`) until the action's signed deadline plus 600 seconds (at most a day, and never less than the counting window), so a byte-identical relay that comes back after the first send was lost and its marks gave way finds the mark and takes none again. The mark is written only after every counter passed, so an action a counter refused is counted afresh when it returns. Only one action per board and nonce (per chair and create nonce for a new board) is in flight at once. A second, different action at the same nonce answers 409 `nonce_in_flight` and moves no counter, so re-signed copies cannot use up other chairs' room.
  - A mark gives way once the action it guards can no longer land. The relay writes the relayer's transaction hash into the in-flight mark (`stampMarks`) before it broadcasts, by compare-and-set. A later action at that nonce takes the mark when the chain does not know that hash or knows it as reverted (`txStatus` answers "unknown" or "reverted"; a transaction reported landed whose receipt says reverted counts the same) (`claimMark`, then `takeDisplaced` under the send lock, where the chain's answer is final). A mark that holds no hash yet blocks others only while the relay that set it is inside its own 55-second deadline. A mark the chain does hold, or cannot answer for, still blocks.
  - Known limits: a send that was lost but lands after its mark gave way can leave two actions at one nonce, of which one lands and the other costs its own fee at the relayer; and the window-open fee may be booked before a later refusal under the lock.
  - Upheld by: `packages/server/src/relay.ts` `handleRelay`, `documentKept`, `hourlyCounters`, `atLimit`, `inflightKey`, `countAndRecord`, `countOnce`, `countedKey`, `claimMark`, `takeDisplaced`, `stampMarks` and `clearMark`; attack `C40-copies` in `security/attacks/relay.ts`.
- C41. A fresh judge never causes a removal, and a removal never costs a guest anything. A join is one add. At a full board it answers 503 `board_full` and nobody is removed. The board keeps DEMO_FREE_SEATS (6) seats free: after a `board_full` answer, and after any admitted join that leaves more than 34 members, a background pressure pass (`schedulePressure`, which hands `freeDemoSeats` to the host's background runner) removes guests until the board is back to 34. Only one pass runs at a time: it holds the mark `demo:pass`, renews it before each removal and releases it at the end, and `freeDemoSeats` answers refused `pass_running` while another holds it, so a full board cannot be used to run passes back to back. The board size the join check keeps is only ever a full one: `boardFull` stores and believes a size at or above the cap, and every other join reads the board itself, so a stale small number can never refuse or admit anyone. Forgetting the size after a removal or an add also clears the flag that says a read is under way, so the next join reads afresh. The pass reads the hour's demo relay room before it scans for keys, so a board where no one can be removed costs no key lookups. Six joins can land between passes before a judge has to wait, and a judge who is told `board_full` waits seconds for the pass, not for a removal of their own.
  - Removals happen only in the scheduled sweep (`sweepDemoGuests`) and the pressure pass (`freeDemoSeats`), both through `removeOneLocked`. The scheduled sweep also runs a pressure pass while the board holds more than 34 members, so seats are freed even where the host has no background runner. The pass and every sweep read a fresh wall clock for each removal (`wallClock`, Date.now when absent), so a pass that starts at 10:59:58 and runs past 11:00 reserves its next removal in hour 11 and books its ledger on the day it happens, not on the time the join arrived. Each removal is its own relay with its own reservation of one of the bot's 120 hourly relays (`reserveDemoRelays`), taken only once there is a target. The target comes from `planRemoval`: a guest with a key problem first, then the oldest guest (reason `pressure`). The pass stops at the first refusal, at a removal whose receipt was not seen, or after six removals. A refused or failed removal changes nothing for any guest, because no guest is waiting inside it.
  - The bot's relays and uploads are booked on its own budgets (12 QOR of the relayer's day, and its own upload allowance), never against a guest's IP, so demo traffic cannot spend the chairs' share or the reverse. A join takes one hourly relay for its add, and these never count against the public per-board, per-chair or valid-action limits. If the hour has none left, the join answers 503 `demo_busy` with the retry-after set to the hour's end. Known limit: a reservation is not given back if a join stops after it was taken. The loss is bounded by the 120 an hour. If an admitted join's receipt is not seen, the next pressure pass signs at the same board nonce and relies on the in-flight mark giving way (C40).
  - Every guest can open a pack. A guest receives the key of the epoch it joins, so packs from earlier epochs stay closed to it, by design. Whenever the board's current epoch has no pack (a removal moved the epoch, or the board was quiet), the demo chair posts the demo pack sealed under that epoch: in the background after every admitted join, after a pressure pass, and at the end of every scheduled sweep (`ensureCurrentPack` in `demo.ts`). It posts at most once per epoch and through the bot's own budgets (its daily share, its hourly relays and the post bytes budget), and a refused post changes nothing for any member. On a record day the posts can use up the demo's daily share before the 120 joins are reached; the share is enforced, so the demo then answers that it is out of budget until 00:00 UTC rather than spend the chairs' share.
  - Upheld by: `packages/server/src/demo.ts` `handleDemoJoin`, `admit`, `reserveRelay`, `schedulePressure`, `freeDemoSeats`, `removeOneLocked`, `planRemoval` and `sweepDemoGuests`; `packages/server/src/relay.ts` `reserveDemoRelays` and `sendLedgers`; `packages/server/src/demoBoard.ts` `uploadEnvelope` and `packages/server/src/blob.ts` `handleUpload` (the internal scope); `packages/server/src/window.ts` `reserveOn`.
- C42. No member's key state can block the removal of another member. A guest whose encryption key is missing, changed or invalid becomes the next guest removed; a problem with the chair's or a seeded director's key raises an alert and removes no one. A member whose key lookup fails the same way (unreadable, not merely slow) on three sweeps in a row counts against that member, and it is removed with the reason `key_unreadable`. One such member can no longer stop the sweep for good. The count moves only on the scheduled sweep; a pressure pass reads it and never adds to it. When a removal lands, that member's count is forgotten, so a guest who is admitted again later does not carry it back in.
  - One ML-KEM key, one member. A guest whose key is byte-equal to another member's is refused at join with 403 `key_shared`. The join compares only against members whose lookup worked, so one unreadable record cannot stop every join. If a copier gets in anyway, the sweep or a pressure pass marks it `key_shared`: it is removed first, whatever its age, and left out of the reseal. No seal is ever made to one key under two accounts, and the board is never frozen. The chain does accept duplicate key registrations (C15, tested live on 19 Nov), so this rule is what stands between a copied key and a seat: the live run showed the bot refusing the copier 403 `key_shared` with the board untouched. Known limit: a copier who publishes a judge's new key first gets that judge refused `key_shared` until the copier's six hours end.
  - Upheld by: `packages/server/src/demo.ts` `refuseSharedKey`, `memberKeys`, `planRemoval` and `sweepDemoGuests`; `packages/core/src/seal.ts` `sealEpochKey`.
- C43. A guest challenge is consumed only by a join that carries a valid signature over it, and at most once.
  - Upheld by: `packages/server/src/demo.ts` `joinProven`, which swaps the stored challenge for a one-minute tombstone by compare-and-set only after the join's signature over it has verified, so a join that proves nothing leaves it in place and a second use finds it gone. Tests: `packages/server/test/demo.test.ts`, and the model test's promises on joins. Live attacks: `C43-challenge-survives` and `C43-replay`.
- C44. Keeping any blob past a short window needs an on-chain reference, and every keep decision can be rebuilt from chain logs. An envelope is kept only if an `EnvelopeGranted` event names its hash. A document is kept only if a `DocumentPosted` event names its hash. A blob with no such event is deleted two hours after its upload, verified or not. A kept document's stored size must equal the size the chain recorded for it. The scan that reads those events marks each hash under a name that includes the registry address (`posted:` and `referenced:`, as the scan keys already were; the posted mark carries the cipherSize the event named) and records how far it has read; the document sweep deletes nothing the scan has not read past, so a scan that is behind, or one starting over after the shared store is lost, can never cause a posted document to be deleted. The marks can always be rebuilt from the registry's deploy block, and nothing hash-named is deleted until the scan has caught up. The shared store runs with eviction off (checked on 19 Nov: `maxmemory_policy:noeviction`), so a mark cannot be dropped to make room.
  - What a stranger can make the store keep is bounded earlier, at the token (C28): 25 MiB per client and 1,250 MiB in total a day (four times the client figure per IPv6 /48), booked when the token is issued, given back once if the token's upload never arrives. Posts are kept for good, so they have a bytes budget too, and it books what we hold, not what the caller claims. The relay relays a POST only when the size we hold for its cipherHash (the verified mark, read by `verifiedSize`) equals the signed cipherSize: otherwise 422 `document_unverified` (no verified mark) or 422 `size_mismatch`, before any counter moves. A post action is refused 429 `post_bytes` when the chair's posted bytes for the UTC day plus that verified size would pass 100 MiB, or the day's total across all chairs would pass 1 GiB. The bytes are reserved before broadcast and given back if nothing was broadcast.
  - A posted blob whose stored size differs from the size its posted mark records is deleted by the sweep (`document_size_mismatch`), whether or not it has a verified mark. A posted mark written before sizes were recorded carries none; such a blob is never deleted for its size, only for a hash mismatch. The document sweep keeps its place in the blob listing across runs, so it reaches every name.
  - Known limit: a document posted more than two hours after its upload is deleted first. The app posts a document right after verifying it. The same holds for an envelope whose action lands more than two hours after its upload.
  - Upheld by: `packages/server/src/envelopeSweep.ts` `sweepUnreferencedEnvelopes` (marks `referenced:<registry>:<sha256>` and `posted:<registry>:<sha256>` with its cipherSize, moves `docsweep:marked-through:<registry>`); `packages/server/src/docupload.ts` `verifiedSize`, `postedSizes`, `sweepUnverified`, `settleTokens` and `returnIfUnused`; `packages/server/src/relay.ts` `documentKept`, `reservePostBytes` and `handleRelay` (the post bytes budget, from `PER_CHAIR_DAILY_POST_BYTES` and `TOTAL_DAILY_POST_BYTES` in `packages/server/src/config.ts`).
- C45. No client signs bytes a server supplied. A guest signs a challenge only through `signChallenge`, and a chair signs a board action only through `signBoardAction`; each rebuilds the bytes from typed fields it checks itself and ignores any `message` or `paramsHash` handed in. Otherwise a compromised challenge endpoint could hand a guest who chairs another board a `ROTATE` for that board labelled as a challenge. `signAction`, which signs any 256 or 224 bytes that carry an Ava tag, is for scripts and the attack suite only.
  - Upheld by: `packages/core/src/sign.ts` `signBoardAction` and `signChallenge`; attack `C33-mirror` in `security/attacks/offline.ts`.
- C46. Copies of a pending action cost nothing. Once an action's exact pre-flight passes, the relay sets a once-only mark on the keccak256 of its calldata, which lives until the signed deadline. A byte-identical copy answers 409 `duplicate` before any per-board, per-chair or total counter moves. The mark is removed if the relay fails before broadcast, so the chair can send the same bytes again. It also gives way like the in-flight mark (C40): it names the relayer transaction once that is known, and a later copy takes it when the chain does not know that transaction or the first relay's own deadline has passed with no transaction. Without this, 60 copies of one action from three IPs used up a chair's and a board's whole hour.
  - Upheld by: `packages/server/src/relay.ts` `handleRelay`, `claimMark`, `takeDisplaced` and `stampMarks`; attack `C40-copies` in `security/attacks/relay.ts`.
- C47. A guest leaves the demo board only by its own signature, and takes nobody with it. The bot removes a guest on request only after that guest has signed a fresh leave message the bot issued for that purpose: its own tag (`ava.leave.v1`), the demo board, the guest's account, a bot nonce and an expiry, signed with the guest's registered, possession-proven ML-DSA-87 key. So nobody can ask for anyone else's removal, and a signature that joins can never be used to leave or the reverse, because the two messages carry different tags and the bot keeps their nonces apart. The chair and the seeded directors cannot be removed this way. A leave request is single use: its nonce is consumed by compare-and-set before anything is sent, and a lost reply on that write never turns a valid request away (C31). Every check the guest can fail (the cross-site rule, the per-address limit, the stored request, the key on chain, the signature, being a guest member right now) runs before the bot reserves, seals, uploads or relays anything, so a refused request costs nothing and changes nothing for any member. The removal itself is the sweep's own: a fresh epoch key sealed to every other usable member, one relay in the demo's scope and budgets, under the lock every board change takes. Afterwards the demo chair posts the next pack for the new epoch (C41), and the guest who left has no key for it. The guest's once-per-address admission stays used: one admission per address, ever (C34). What it does not cover: the guest keeps every pack it could already open, as any removed director does, and the screen says so.
  - In the browser the guest signs the leave only through `signLeave`, which builds the bytes from typed fields the page checked itself (C45), after the guest pressed a control that says what it does.
  - Having left, the guest's browser tries to open the pack the chair posts next, and says it is shut only from its own failed attempts: the pack's stored bytes match the registry's size and hash, every envelope of the new epoch was downloaded and refused the guest's own keys as not a recipient, and the key of the epoch the guest last held was opened again and failed on the new pack. A read that fails gives no verdict, and anything that opens is shown as a fault, never as a lock.
  - Upheld by: `packages/core/src/actions.ts` `leaveMessage`; `packages/core/src/sign.ts` `signLeave` and `signAction` (which refuses leave bytes); `packages/server/src/demo.ts` `handleDemoLeaveChallenge`, `handleDemoLeave`, `leaveOnce`, `planRemoval` and `leaveKey`; `packages/web/lib/guest/leave.ts` `checkLeaveRequest`, `requestLeave`, `confirmLeave` and `removalIn`; `packages/web/lib/guest/shut.ts` `tryEveryEnvelope`, `tryOldKey` and `waitForShutPack`; attacks `C47-forged-leave`, `C47-leave` and `C47-leave-once` in `security/attacks/demo.ts`. The refusal of the chair and the seeded directors, the refusals on the bot's side and the lost-reply case are proven by unit tests, named under `C47-protected` and `C47-refusals` by `npx tsx run.ts --list` in `security/`; the orderings are promise 18 of the model test below.
- Accepted, not fixed: boardRef squatting. Board refs are unique per registry, so someone watching pending transactions could create a board with a victim's pending boardRef first. The victim's creation fails with BoardRefUsed and the app retries with a new boardRef, a fresh epoch key and a fresh envelope. It never reseals the first key, because `createBoard` accepts any envelope hash and the squatter can copy the victim's epoch 0 envelope hash onto the squatted board, which would hand the squatter a key that is still in use. No board's confidentiality is affected, because a place is never shared between two boards.

### How the timing promises are tested

Unit tests check one case at a time. The promises above are about order and time: what happens when a reply is lost, a request is retried, two requests overlap, or the clock moves on between two steps. So a randomised model test (`packages/server/test/model/`) drives the real relay, demo and document handlers against a simulated chain and store. Each run builds a fresh world, then plays up to 60 random steps: relays, joins, uploads, sweeps and pressure passes. Requests overlap at every store and chain call, so the test sees what two requests do when each pauses between any two of its steps. The simulated chain can be slow, lose a transaction, lose a receipt, report a wrong receipt, or use the relayer's nonce for a transaction of its own. The store can apply a write and lose the reply on most writes, increments included, so the caller retries a write that already landed. The clock can jump by seconds, minutes, hours or days. After every step it checks 16 promises:

1. Every handler answers and none throws.
2. The per-board, per-chair and valid-action hourly counters equal the distinct actions handed to the chain in their window.
3. No join removes anyone, and every removal is a sweep's, a pressure pass's or a signed leave's, of a guest.
4. An admission mark belongs to a member, to a guest once seated, or to an add still pending; a dead add's mark never refuses its guest and never survives a sweep.
5. Each day's booked spend covers the real fees of what landed, is never negative, and every share stays under its ceiling.
6. The relayer halts exactly when a foreign transaction used its nonce, and never otherwise.
7. Post bytes booked equal the verified sizes of the posts handed to the chain, no kept document differs from a posted size, and token bytes stay under their daily caps.
8. Once a mark's transaction is unknown to the chain, a different action at that nonce can be relayed.
9. A write retried after a lost reply never makes a ledger or a byte budget show less than was booked and not given back.
10. Two different actions at one board nonce, or two copies of one action, are never both handed to the chain while the first is pending.
11. A join refused because the board is full or the bot is busy takes nothing, sends nothing and leaves no mark.
12. No sweep's or pass's removal takes the demo board below its floor of 34 members unless its guest was due anyway.
13. Each share of the day's spend stays under its ceiling.
14. A relay that moved the hourly counters handed a transaction to the chain or was refused by one of them.
15. A dead add's mark never refuses its guest.
16. A guest the bot never sent an add for is never refused as already admitted or as unsettled, unless another join of it ran at the same time.
17. The bot posts a pack only for an epoch that has none, at most one per epoch, and every guest who held that epoch's key can decrypt it.
18. A leave removes only the account that signed it, at most once for each leave request, and only on that account's own signature over a leave request the bot issued. A leave its sender could have failed costs nothing, no leave admits anyone, and nobody taken off the board can open a key of the board's current epoch.

The normal suite runs 300 such sequences; a deep run does 2,000 (set `MODEL_RUNS=2000`). A failure prints its seed and the shortest sequence that breaks a promise, and the same seed replays it exactly. The test is checked against itself: eighteen bugs were planted one at a time in the code, three of them in the pack posting and eight in the leave, and the test caught every one within 2,000 runs (the slowest on run 1,229). The last deep run, 2,000 runs on seed 20261119, held all 18 promises; in it the bot handed 1,977 pack posts to the chain, 64,493 guest opens of those packs were checked, 1,192 leaves were accepted, and 2,015 forged ones (another signer, the join's bytes, a join's nonce, or a leave sent to the join endpoint) removed and admitted nobody. What it does not cover: lock races between server instances, a store that fails outright, the real chain and the real stores, `createBoard` and `transferChair` relays, fee spikes, and the sponsor and chain proxy. The live attack run covers part of that; the rest is a stated limit.

### Audit, 19 Nov 2026

After the backend was proven on testnet, six separate read-throughs were run, one per area and each blind to the others: the contract, the message format, encryption and keys, the relay and its window, the demo bot and sponsor, and the proxy and uploads. They found 11 important issues. All 11 are fixed, each with a test that failed before the fix. Two code reviews of those fixes then found 8 more gaps, 4 in each review, and they were fixed the same way, with a test that failed first. The first review's four were a copied encryption key on the demo board, the demo's hourly relay room, the relayer's stored nonce, and the IPv6 /48 rule at three limits. The second review's four were a post budget that counted the size the caller claimed, a refusal a caller can cause placed after a shared counter, a mark that outlived the action it guarded, and the /48 rule missing from the upload budgets. After the second review the demo join was redesigned: it had been two steps at a full board (remove the oldest guest, then add the newcomer), and every review found a new way for it to stop between the two and evict a guest for nothing. A join is now one add and never removes anyone (C41). One further finding, that an expired relayer window reads as zero spent, was disproved by a live read: the chain's REST keeps `used_txs` and `used_value` after expiry. A randomised model test of the timing and ordering promises (see "How the timing promises are tested") then found two further ordering bugs the reviews had missed: a retried action was counted twice against the hourly limits, and a write that landed with a lost reply locked a guest out of the demo for 150 seconds. Both are fixed, and the sequences that exposed them now pass. A final review of all these fixes found two more gaps (a lost reply refusing a valid join, and a daily upload total that too few addresses could spend) and a lock that could block everyone after a lost reply. All are fixed, each with a test that failed first. The model test was then made harder: requests overlap at every store and chain call, most writes including increments lose their reply, and it checks 16 promises instead of 8. It found six more ordering bugs the code reviews had not, all fixed: a send that reverted kept its copy mark, an unsettled list outlived by its marks, a give-back that doubled when its reply was lost (in the relayer's window and in the upload budget), a board-full reading that outlived its cache, an unsure board read answered as a refusal, and counters kept for a send that timed out before it was broadcast. It also showed that two joins of one guest at the same moment were answered 409; they now get 503 `admission_unsettled` and a retry. In all, the two earlier bugs included, the model test found 8 ordering bugs the reviews had missed, every one fixed. To check that the test itself can fail, bugs were planted one at a time (eighteen by now) and it caught every one. Tests today: 139 on the contract, 80 in the core library, 320 on the server and 135 in the web app. The reports are not public; they are kept with the project's private notes. The attack suite and the unit tests named in `security/README.md` prove each fix. The last live attack run (23 Nov, `security/results/run-20261123T082453Z.md`) held 76 of 77 claims, with 0 not held and 1 not run: `C36-drill-key`, which waits for the drill key to be published.

### C.7 The five general standards, applied here

1. Primitives over lists. Each check says what it covers and what it does not.
- "Is this a real board" is answered by the registry's own record. It covers every board ever made with nothing to maintain. It does not cover a registry we did not deploy, so the registry address is a constant fixed at build time.
- "Is this action valid" is answered by an eth_call of the exact transaction. The contract is the check, so there is no second signature checker that can drift from it. It does not cover state changing between the call and inclusion, which only makes the transaction revert.
- "Where does the proxy go" is answered by origin equality on the parsed URL, which covers every host trick at once. The route list next to it is an allowlist that fails closed: a missing entry breaks a feature and never opens a hole. The list exists to stop the proxy being a free general-purpose proxy, not to stop request forgery.
- "Is this an address" is answered by the bech32 and hex codec with checksum, never a regular expression. It does not cover a valid address belonging to the wrong person (C21, non-goals).
- "Is this a KEM key" is answered by QoreSeal's validateMlkemPublicKey, the same check the chain applies. It does not cover a valid key that belongs to someone else (C15).
- "Could this signature be something else" is answered by a fixed length, a tag that is not valid UTF-8 and a leading length that exceeds the message (C3), checked against every sign-bytes builder in the pinned SDK. It covers every form that exists today. It does not cover a form a later SDK adds, so the check is run again whenever the SDK changes. It also cannot cover other contracts that ask the same account key to sign raw bytes through pqcVerify: C3 is a promise about Ava's messages only.
- "What can we preview" is answered by an allowlist of types detected from the bytes. We never keep a list of dangerous types.

2. Normalize before you compare.
- Addresses: one codec, compared as 20 bytes (C16).
- Recovery phrases: one function, `canonicalPhrase`, and only its output reaches any key derivation, in the browser and on the server (C16).
- Signed messages: one encoder, with a shared test vector (C4).
- Hashes: SHA-256 over raw bytes in the upload, record and read paths, compared as bytes32, never as hex strings that might differ in case.
- URLs: the URL object that was checked is the one that is fetched (C22, C30).
- Purpose and AAD: one builder each (C13).
- Chain identity: EVM chain id 9800 in signed messages and `qorechain-diana` in QoreSeal, both from one module of constants.
- Time: deadlines in seconds, taken from the latest block's timestamp, not from the browser clock.

3. Validate outputs like inputs.
- Proxy responses are checked and relabelled before they reach the browser (C22).
- The URI the upload endpoint returns is checked against the expected form before the chair signs it, because a signed URI stays on chain for good.
- A relay transaction hash is confirmed on chain before it counts (C26).
- Blob bytes are hash-checked before use (C12, C30).
- Chain strings and decrypted documents are rendered as plain text or inside a sandbox (C19, C20).
- The bot's addMember is a write to the chain and gets the same checks as a chair's (C33 to C35).
- The ledger is a security claim shown to judges, so it says "incomplete" rather than show a partial answer (C38, C39).
- Upstream error text is never echoed into HTML, and log lines never carry secrets (C32).

4. Fail closed.
- Contract: empty precompile data, pqcVerify false, possessionProven false, wrong epoch, used nonce, expired or too-distant deadline: revert.
- Browser: KEM `found: false`, any hash mismatch, an envelope parse error, a GCM failure, an unexpected epoch payload: stop and show the error, never partial plaintext.
- Server: a failed simulation, a reached budget, a failed window renewal, any failed lookup in the sponsor: refuse.
- Limits, all explicit: upload byte cap, relay body cap, proxy response cap and timeout, RPC timeouts, envelope cap, MAX_MEMBERS, URI length cap, deadlines at most one hour ahead, a maximum page count when reading logs.
- Defaults: narrow windows, no CORS, blobs that cannot run, separate accounts with small balances, and `mlkem` mode only as an explicit choice.

5. Non-goals: what this design does not defend against.
- The chair, or anyone holding the chair's key or device. The chair can read everything and seal the epoch key to anyone. The contract cannot see who an envelope is sealed to; C39 catches extra recipients only in recorded envelopes.
- What a removed director already received. They keep every epoch key they were given and can read those documents forever, because the ciphertexts are public. Removal protects only documents posted afterwards. The exposure ledger exists to show this honestly.
- Metadata. Board membership (as addresses), document counts, sizes, timing, epochs and removals are all public on chain.
- A director's own compromise: malware, a hostile browser extension, physical access, a weak passphrase, or a lost mnemonic. There is no recovery; the data is gone.
- A compromised npm dependency or build pipeline. Pinned versions and a lockfile reduce this risk; they do not remove it.
- A flaw in QoreSeal 0.1.0 (pre-1.0, its construction is pending external review) or in ML-KEM-1024. `mlkem` mode has no classical X25519 layer to fall back on.
- Censorship by the relayer. It cannot forge, and the nonce stops it reordering, but it can delay or drop an action. A chair can always submit the signed action from any funded account instead.
- Copying of relayed actions from the mempool. The copy has the effect the chair intended; the relayer pays for its own reverted duplicate, and rate limits bound how often.
- Scripted identities draining the sponsor and the relayer, up to their daily ceilings.
- The demo board's documents. They are public by design: every guest receives the key, and the bot's server holds it.
- The chain publishing a copied ML-KEM key. The KEM registry asks for no proof that the registrant holds the private key, by design (QoreChain documents why), so anyone can register another account's public key as their own (C15). We cannot stop that, and it is not a chain bug. We only refuse to seal to a key listed under two accounts and to seat its second holder. The copier cannot decrypt anything sealed to the copied key.
- The chain itself. Its PQ key registry, KEM registry and precompiles are trusted. Board authority follows the chair account's current registered key, so anything the chain allows to replace that key moves the board along with it.
- The out-of-band address exchange. If a director's address is swapped on its way to the chair, the wrong person is invited.
- Old signatures after a testnet reset. Only the one-hour deadline limits them.
